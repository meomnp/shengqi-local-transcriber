## PyAV 18.1.0 Windows wheel / bundled FFmpeg audit flag

- Installed wheel tag: `cp311-abi3-win_amd64`; PyAV package metadata calls its source BSD-3-Clause. Runtime `avutil_license()` reports `LGPL version 3 or later`; `avcodec_configuration()` reports FFmpeg 8.1-era options including `--enable-version3`, `--enable-libx264`, and `--enable-libx265`. The runtime also registers `libx264` and `libx265` encoders.
- The packaged `av.libs` includes FFmpeg DLLs, `libx264` and `libx265`, but carries no corresponding license/source bundle at that location. The PyAV v18.1.0 release says its binary wheels ship FFmpeg 8.1.2: https://github.com/PyAV-Org/PyAV/releases/tag/v18.1.0
- A read-only PE import-table check of the installed Windows candidate found that `avcodec-62-...dll` directly imports both `libx264-...dll` and `libx265-...dll`. Therefore deleting those two DLLs from the existing package is not a valid mitigation; the FFmpeg/PyAV binaries must be rebuilt or replaced as a compatible set, then exercised through packaged GUI, transcription, and all four audio export formats.
- PyAV upstream issue #2270 is disputed and must not be summarized from its title alone. The issue author argues the PyPI wheels are GPL; a maintainer replied that the `--enable-gpl` flag is used in a test build, not the shipped wheel, and separately stated the wheel route as “LGPLv2.1 or later + Commercial exceptions” OR “GPLv2 or later.” When asked where to apply the exception, the maintainer pointed to x264/x265 project licensing pages and said the choice is implied by distribution behavior or may be explicitly stated. This exchange is useful upstream context, but it does not provide a self-contained, version-specific downstream grant/terms document for this app to retain. The exact x264/x265 binaries and terms, their corresponding-source obligations, and the selected route remain unverified: https://github.com/PyAV-Org/PyAV/issues/2270
- The matching `pyav-ffmpeg` 8.1.2-1 tag is commit `a71bf9279f7a4659154b68ba6783e89be460bcd5`. Its README lists x264 and x265 as built packages, and its build script adds `--enable-libx264` and `--enable-libx265` on non-32-bit-ARM platforms. The repository tree at that tag has no top-level `LICENSE`/`COPYING` file. The source tree is valuable build provenance, but its existence alone does not establish the complete redistribution package or the exact license route for the wheel.
- FFmpeg's official legal page says GPL components can make the entire FFmpeg build GPL and warns distributors to verify `libx264` and linked dependencies: https://www.ffmpeg.org/legal.html
- FFmpeg's own checklist identifies an LGPL route as requiring a build without `--enable-gpl`/`--enable-nonfree`, dynamic linking, exact corresponding source, build/configuration instructions, and further review of external LGPL libraries; it explicitly calls out avoiding GPL libraries such as libx264. The current wheel's upstream build sources include x264/x265, so an “LGPL only” assumption cannot be made from the runtime `avutil_license()` string alone: https://www.ffmpeg.org/legal.html
- Decision: **not release-cleared**. A potentially cleaner path is to build/use a minimal FFmpeg/PyAV configuration without GPL codecs (the app only decodes media and exports audio) and prove it still passes the app's format/transcription tests; this is a technical option to investigate, not a completed compliance finding. Otherwise obtain and retain the exact applicable exception terms, source/build inputs, and redistribution notices for every bundled binary. Then select a compatible app-source license with the owner. Do not describe the present bundle as simply BSD or MIT.

## PyAV 17 LGPL-wheel technical probe (2026-10-06; not release-cleared)

- Candidate source: https://github.com/kazuki/PyAV-LGPL-Binary-distribution, release tag `20260602`, wheel `av-17.0.1-cp311-abi3-win_amd64.whl`; SHA-256 `E5185E6ACA207C0BB741EA3A8BA2896765929A70413D240FD1064C8F220A5A02`. Its release title identifies `PyAV-v17.0.1 + ffmpeg-n8.1.1-9-g58d4114d36-20260602`; its README build recipe, however, downloads BtbN's mutable `latest` URL. A same-day BtbN page identifies release `autobuild-2026-06-02-14-20` and build-repository commit `6e66d4d1e81f75b5f34dc2a369cc341e12edc531`. Read-only GitHub API queries now return 404 for that release/tag and do not list its binary assets; the build-repository commit itself remains available. Thus the wheel's release metadata gives a strong version/date correlation, but the README alone does not prove the actual Windows archive, its SHA-256, and all build inputs used. Treat this as a third-party probe artifact, not an approved distribution dependency.
- Runtime inspection of the wheel's bundled FFmpeg reports LGPLv3-or-later; its configuration disables `libx264` and `libx265`, and its avcodec DLL import table does not import either codec. This is materially different from the app's current PyAV 18.1.0 bundle, but runtime configuration alone is not proof of complete downstream compliance.
- A separate BtbN FFmpeg LGPL shared archive was inspected for comparison: tag `autobuild-2026-10-05-13-07`, file `ffmpeg-n8.1.3-14-g330caae0c1-win64-lgpl-shared-8.1.zip`, SHA-256 `534653068A3AC64ED5D02361E1AD59E4CB99A713F425444B470514999E437473`. Its FFmpeg configuration disables x264/x265 and GPL/nonfree flags. This archive is not established as the exact input used to build the PyAV wheel above, so do not treat it as that wheel's corresponding source or provenance.
- Compatibility evidence is from an isolated PyInstaller rebuild using PyAV 17, not from modifying the installed candidate: the probe EXE self-test passed; its packaged GUI create/update/destroy smoke exited 0; with synthetic black video plus synthetic speech it exported MP3, M4A, WAV, and FLAC, each successfully decoded by FFprobe; bundled `small` model performed offline CPU/int8 transcription and correctly returned the three known synthetic English sentences with timestamps. No user media was read. This is not a visual acceptance or clean-machine test. The first approach of overlaying only the wheel onto the existing frozen app failed because stale PyAV 18 Python modules remained; a clean rebuild is required for a PyAV version change.
- The probe build showed dependency-resolution warnings (including an optional `onnxruntime.quantization` import without `onnx`, and a PyYAML shadowing issue in one build environment). Core self-test, four audio exports, and synthetic transcription did pass, but this does not establish that every optional feature or all environments are healthy. Preserve the probe output outside any user-facing package until the build recipe and warnings are resolved.
- Decision: this is a technical direction worth pursuing, not a release approval. Before redistribution, obtain exact immutable upstream sources/build inputs for every bundled FFmpeg/PyAV binary, determine the complete license/notice/source obligations, rebuild reproducibly in a clean supported Python environment, resolve warnings, rerun the complete GUI/package test suite, and obtain owner approval for the app's own source license and the exact GitHub destination.
